    1. Executive Summary

    149 requires one navigation contract across the KITScenes Lanelet2 training

    path and the OSM/Valhalla runtime path:

    destination
    -> RouteProvider
    -> provider-native global route
    -> LocalLaneSequenceResolver
    -> NavigationRoute
    -> C++ ego-local rasterizer
    -> map_context + route_mask + validity + provenance

    OSM and Lanelet2 are adapters behind this contract. They are not separate model interfaces. The first runtime RouteProvider is a vehicle-local Valhalla service backed by prebuilt regional tiles. KITScenes training derives the same NavigationRoute contract by matching each complete scene trace to its Lanelet2 map.

    The training route must not contain the exact future ego trajectory. Directly drawing the 64 future ground-truth points would disclose the target that the model is trained to predict. KITScenes therefore reduces a complete scene to a sequence of selected lanelets. Rasterization uses a fixed-width corridor around the selected lanelet centerlines and never draws a sample-specific lateral lane-change trajectory.

    The initial information boundary is:

    semantic map raster --+
                      +-> validity gate -> channel concat
route raster ---------+                    -> navigation encoder
                                           -> Reactive BEV fusion
                                           -> Reactive planner at 10 Hz

visual/ego context ---------------------------> Reasoning branch

    The route enters only the Reactive branch in the initial implementation. It is not supplied to HorizonReasoningHead, its teacher prompt, or a Reasoning-specific cache. map_context, route_mask, map_valid, and route_valid remain separate at the public API and storage boundaries; the model concatenates the gated tensors immediately before its navigation encoder.

    Map and route rasters are generated by an authoritative C++ renderer at about 2 Hz by decimating 20 Hz localization by ten. A 10 Hz camera/model tick uses timestamped localization to apply a cheap SE(2) warp from the latest raster to the camera timestamp. Routing, map matching, tile building, and network access are never performed in the 10 Hz loop.

    Flyte preprocessing reproduces the same temporal contract: it renders deterministic 2 Hz anchor rasters and applies the production SE(2) warp to each 10 Hz sample. Training therefore does not receive perfectly re-rendered map pixels that are unavailable at runtime.

    The work is complete only after a new immutable KITScenes dataset version has been produced, a route-conditioned model has been trained, and its result has been compared with a controlled no-route baseline on the existing benchmark plus junction, maneuver, route-compliance, and offline counterfactual slices.

    2. Architectural Decisions

    2.1 Information-flow boundary

    The initial model has two explicit navigation inputs:

    • map_context and route_mask are gated independently by their explicit validity inputs.
    • map_context, route_mask, map_valid, and route_valid remain separate in the public data and model ABI.
    • The gated map and route tensors are channel-concatenated and encoded by the Reactive navigation encoder.
    • The resulting spatial features are passed to MapBEVFusion.
    • Route tensors and route-derived features are never supplied to the Reasoning branch in the initial implementation.

    This boundary makes Reactive-only route conditioning observable and testable. Reasoning-only and combined Reasoning/Reactive conditioning remain future ablations.

    The baseline semantic map contains drivable area, lane boundary, centerline, intersection, crosswalk, stop line, static traffic-signal position, traffic direction, map validity, and road-level information when available.

    2.2 Rejected initial alternatives

    • Exact future-waypoint raster: rejected because it discloses the imitation target rather than navigation intent.
    • Manual offline route annotation for inference: rejected because it is not a production navigation interface.
    • Independent OSM and Lanelet2 raster contracts: rejected because they would create incompatible training and inference geometry.
    • Route input to the Reasoning branch: deferred so the first experiment isolates Reactive-only route conditioning.
    • Python or network-dependent vehicle rendering: rejected in favor of a deterministic C++ renderer over locally cached vectors.

    3. Goals and Non-Goals

    3.1 Goals

    1. Define one provider-independent vector and raster navigation ABI.
    2. Support Lanelet2 and OSM through separate adapters.
    3. Derive a lane-sequence route from KITScenes without exact-trajectory leakage.
    4. Provide a realistic local Valhalla runtime reference instead of manual route annotation.
    5. Use one authoritative C++ rasterizer in preprocessing and inference.
    6. Align navigation pixels exactly with the camera BEV metric frame.
    7. Preserve route, raster, validity, quality, and provenance losslessly.
    8. Feed route information only through the Reactive branch initially.
    9. Train and evaluate the route-conditioned model through Flyte.
    10. Show the selected route, destination, validity, and quality in DataModelConsole.
    11. Keep route-less lane following functional.

    3.2 Non-goals for the initial implementation

    • L2D or NVIDIA PhysicalAI-AV route training.
    • Cloud routing or live Overpass access from the vehicle.
    • Buildings, vegetation, shop names, or other decorative OSM layers.
    • Exact lateral lane-change trajectories.
    • Alternate-route model input.
    • Closed-loop evaluation.
    • Map/route dropout, synthetic wrong-route training, or localization/yaw augmentation.
    • Separate pretraining of navigation or visual encoders.
    • The full map-only/route-only/map+route/blank/shuffled/wrong-route ablation matrix.
    • Route conditioning of the Reasoning branch and a Reasoning-state cache.

    Encoder pretraining and broad route-robustness ablations are future work items outlined in Section 20.

    4. Existing State and Gaps

    4.1 KITScenes

    Model/data_parsing/kit_scenes/map.py already renders a 256 by 256 tile over a 120 m by 120 m area:

    radius_meters = 60
meters_per_pixel = 120 / 256 = 0.46875

    Its important gaps are:

    • no selected route;
    • no route vector artifact;
    • palette RGB instead of fixed semantic channels;
    • ego centered instead of aligned with the camera BEV origin;
    • no per-layer or sample validity;
    • no fixed frame/geometry ABI;
    • Python/OpenCV rendering through a 2048 by 2048 supersampled canvas;
    • lossy JPEG storage in the current shard path.

    The current camera BEV default is also not the same geometry. It uses pc_range=(-60, -60, -5, 120, 60, 3), which is 180 m longitudinal by 120 m lateral and places the ego one third from the rear edge. A square 256 pixel raster with square 0.5 or 1.0 meter pixels cannot exactly match that rectangular range. Geometry must be selected jointly; it cannot be fixed by resizing one branch.

    4.2 OSM

    Model/data_parsing/map_rendering/gps_to_map.py currently:

    • downloads through Overpass;
    • performs nearest-node matching;
    • fills gaps with NetworkX shortest paths;
    • draws with Matplotlib;
    • outputs a 640 by 360 RGB image;
    • can draw the raw GPS points and matched route in the same image.

    This is an offline prototype, not a vehicle runtime. It must be replaced by a local vector-map adapter and the common C++ rasterizer. Live Overpass requests are prohibited.

    4.3 Reasoning

    HorizonReasoningHead already accepts an optional route_context, but the initial #149 implementation deliberately leaves it unset. Existing Reasoning labels and prompts remain route-agnostic. Reasoning scheduling and caching are separate concerns and do not gate Reactive route conditioning.

    4.4 Why training and runtime need one contract

    Implementing the KITScenes and OSM/Valhalla paths independently would create:

    • two incompatible pixel geometries;
    • two route semantics;
    • separate model inputs;
    • training/inference skew;
    • duplicated rendering code.

    The common contract freezes semantics first. Provider adapters then supply canonical vectors to one rasterizer.

    5. System Architecture

    5.1 Offline KITScenes path

    KITScenes scene
  |-- Lanelet2 map
  |-- complete ego pose trace
  |
  +-> Lanelet2MapAdapter
  +-> Lanelet2TraceMatcher
        |-- pose + heading candidates
        |-- traffic-rule filtering
        |-- sequence continuity
        |-- routing-graph gap fill
        |-- adjacent-lane transitions
        v
      NavigationRoute + RouteQuality
        |
        +-> C++ rasterizer at deterministic 2 Hz anchors
        |     |-- semantic map channels
        |     |-- route corridor
        |     |-- destination marker
        |     +-- validity/metadata
        +-> production SE(2) warp for each 10 Hz sample
        |
        +-> Flyte shard schema v5
        +-> train_il
        +-> evaluate + Console

    The expensive route derivation is performed once per scene inside Flyte data_processing. Vector clipping and rasterization run only on deterministic 2 Hz anchors. Per-sample work applies the same timestamped warp used at runtime.

    5.2 Runtime path

    user destination
  -> local Valhalla /route request
  -> ValhallaRouteProvider
  -> OSM local lane graph
  -> LocalLaneSequenceResolver
  -> NavigationRoute revision N
  -> atomic route store

20 Hz localization
  -> decimate by 10
  -> C++ rasterizer at about 2 Hz
  -> timestamped NavigationRaster

10 Hz camera/model tick
  -> select latest complete raster revision
  -> SE(2) warp to camera timestamp
  -> map_context + route_mask to Reactive navigation encoder
  -> Reactive planner

    Valhalla is a global routing provider, not a Lanelet2 route provider. A raw Valhalla polyline is not accepted as the canonical lane sequence. It must first be resolved against the onboard local lane graph. Where OSM has sufficient lanes and turn:lanes attribution, the OSM adapter materializes stable directed lane segments. Missing lane detail lowers route confidence and is recorded; it must not be silently represented as exact HD-lane knowledge.

    6. Vector Contracts

    6.1 Coordinate frames

    All adapters must make frame conversion explicit:

    1. Provider frame: WGS84, provider tile coordinates, or Lanelet2 map frame.
    2. Canonical map frame: local ENU meters.
    3. Model frame: ego FLU meters, with +X forward and +Y left.
    4. Pixel frame: row downward and column rightward.

    No adapter may return an unlabelled x, y array. Every vector object carries a frame identifier and map origin/projection metadata.

    6.2 NavigationRoute

    The canonical route is a selected ordered lane-segment sequence:

    NavigationRoute
  schema_version: string
  route_id: string
  revision: uint64
  provider: string
  timestamp_ns: int64
  valid_from_ns: int64
  map_version: string
  frame: MapFrame
  lane_sequence: List[RouteLaneSegment]
  destination: Destination
  confidence: float32 in [0, 1]
  valid: bool
  quality: RouteQuality
  estimated_destination: bool
  provenance: RouteProvenance

    The metadata fields route_id, revision, timestamp_ns, map_version, provider, confidence, and valid are mandatory.

    Each RouteLaneSegment contains:

    lane_id: stable canonical string
provider_segment_id: provider-native identifier
centerline_enu_m: N by 3 float64
left_boundary_enu_m: optional N by 3 float64
right_boundary_enu_m: optional N by 3 float64
level: optional int32
transition_from_previous:
  follow | left_adjacent | right_adjacent | merge | split
maneuver:
  straight | left | right | u_turn | merge | exit | destination | unknown
confidence: float32

    For Lanelet2, lane_id includes the Lanelet2 ID. For OSM, it is a stable directed lane identifier derived from map version, OSM way/edge direction, and lane index. Provider-native IDs remain available for debugging but never become the model ABI.

    6.3 Route semantics

    • Only the selected route is stored as model input.
    • The full route to the destination is retained in vector form.
    • A raster contains only the local crop.
    • At most 10 m of route behind the ego is retained in the crop.
    • A destination marker is rendered only when the destination lies inside the crop.
    • A lane change is represented by adjacent-lane transition metadata and the selected lane segments. No interpolated lateral movement line is generated.
    • The route raster is a fixed-width corridor. One width is selected from the KITScenes lane-width audit and frozen per dataset/model contract version. Width is configuration and provenance, not an implicit renderer constant.
    • Alternative routes are not model inputs.

    6.4 NavigationMap

    Map adapters emit canonical semantic primitives, not colored pixels:

    NavigationMap
  schema_version
  map_version
  provider
  frame
  bounds
  drivable_polygons
  lane_boundaries
  lane_centerlines
  intersection_polygons
  crosswalk_polygons
  stop_lines
  static_traffic_signals
  directed_lane_fields
  primitive_levels
  layer_availability
  provenance

    Buildings and vegetation are deliberately absent from the initial contract. The static position of a traffic signal is map context; its current color is a camera/perception concern.

    7. Raster Contract

    7.1 NavigationRasterGeometry

    Raster geometry is immutable and versioned:

    geometry_id
height_px = 256
width_px = 256
meters_per_pixel
x_min_m, x_max_m
y_min_m, y_max_m
ego_anchor_row, ego_anchor_col
frame = ego_flu
pixel_convention
matching_pc_range
matching_bev_h
matching_bev_w

    The following invariants are enforced:

    (x_max_m - x_min_m) / height_px == meters_per_pixel
(y_max_m - y_min_m) / width_px == meters_per_pixel
map extent == camera BEV pc_range XY extent
ego anchor == the origin implied by pc_range
(x_max_m - x_min_m) / bev_h == (y_max_m - y_min_m) / bev_w

    The renderer must output the final dimensions directly. A route mask is never resized with bilinear or bicubic interpolation. Any required mask resize uses nearest-neighbor interpolation, but the production path should require no resize.

    7.2 Geometry selection gate

    The geometry audit is recorded in Docs/navigation_geometry_audit.json. It uses the 404 non-empty KITScenes v2.2 scene-path artifacts and 60,443 valid 6.4-second horizon pairs. The measured distribution is:

    Quantity p50 p90 p95 p99 max
    Speed (m/s) 7.15 13.60 15.51 20.68 28.20
    6.4 s displacement (m) 44.15 86.57 100.25 131.35 178.81
    Absolute lateral displacement (m) 2.44 14.89 22.81 38.21 59.26

    The candidates cover:

    Resolution Longitudinal extent Lateral extent Coverage
    0.5 m/px 42.75 m rear, 85.25 m front 64 m each side 89.31%
    1.0 m/px 85.5 m rear, 170.5 m front 128 m each side 99.79%

    The selected initial geometry is kitscenes-v3-bev-1m-v1: 256 by 256 pixels, 1.0 m/px, x=[-85.5, 170.5], y=[-128, 128], ego anchor (row=170.0, col=127.5), and matching camera BEV pc_range=(-85.5, -128, -5, 170.5, 128, 3). Pixel coordinates refer to cell centers. Camera BEV and navigation geometry change together.

    7.3 Semantic map channels

    The baseline uses fixed semantic channels:

    Index Channel Storage/model range
    0 drivable area binary / [0, 1]
    1 lane boundary binary / [0, 1]
    2 lane centerline binary / [0, 1]
    3 intersection binary / [0, 1]
    4 crosswalk binary / [0, 1]
    5 stop line binary / [0, 1]
    6 static traffic signal binary / [0, 1]
    7 traffic direction sin, encoded as (sin + 1) / 2 float32 / [0, 1]
    8 traffic direction cos, encoded as (cos + 1) / 2 float32 / [0, 1]
    9 traffic direction valid binary / [0, 1]
    10 known map area binary / [0, 1]
    11 road level, versioned normalized encoding float32 / [0, 1]
    12 road level valid binary / [0, 1]
    13 overlapping-level ambiguity binary / [0, 1]

    The vector map always retains level when the provider supplies it. At a raster overlap, the initial renderer selects the ego/route-connected level and marks ambiguity. It must not merge a bridge and road into an unexplained single drivable surface.

    The model receives float32 in [0, 1] without ImageNet RGB normalization. Binary layers may be stored as uint8 and converted losslessly at load time.

    7.4 Route channels

    route_mask is separate from map_context:

    Index Channel Storage/model range
    0 selected fixed-width route corridor binary / [0, 1]
    1 destination marker binary / [0, 1]

    The persisted mask is binary and lossless. route_valid is also supplied as a sample-level scalar; an all-zero mask alone is not used to distinguish "no route", "destination outside crop", and "render failure".

    map_valid and route_valid are explicit model inputs and are included in evaluation output.

    8. KITScenes Route Derivation

    8.1 Scene-level matching

    The entire scene trace is matched once. It is not matched independently for each 64-step training target.

    For every pose:

    1. Query candidate lanelets within a configured metric radius.
    2. Score position and heading, using probabilistic matching when covariance is available.
    3. Remove candidates that violate participant traffic rules.
    4. Use sequence optimization across the full scene so isolated nearest-lane choices cannot jump between disconnected or opposite-direction lanelets.
    5. Fill non-adjacent matched gaps with the routing graph shortest path.
    6. Preserve valid left/right adjacent transitions as lane changes.
    7. Deduplicate consecutive lanelet IDs while retaining transition metadata.

    The sequence optimizer records its distance, heading, traffic-rule, transition, and gap-fill costs in versioned matcher configuration. Tie-breaking is stable and deterministic.

    8.2 Destination

    The final valid matched scene lanelet and final scene position form the training destination. This is an estimated destination, not a user-entered navigation goal, so:

    estimated_destination = true
destination_source = "kitscenes_scene_end"

    must be present in the route artifact and dataset manifest.

    8.3 Failure and quality policy

    A failed sample is not silently removed. It receives:

    route_valid = false
route_mask = zeros
RouteQuality.failure_reason

    Scene-level quality includes:

    • matched-pose ratio;
    • median and p95 lateral match distance;
    • median and p95 heading error;
    • number and length of shortest-path fills;
    • number of adjacent-lane transitions;
    • unresolved discontinuities;
    • confidence;
    • failure reasons.

    Before the full repack, a route-audit Flyte task measures the corpus and freezes scene-exclusion thresholds in configuration. The policy is:

    • keep individual invalid samples as route-less samples;
    • exclude a scene from route-conditioned training when valid route coverage is below the audited threshold, an unresolved discontinuity remains, or the configured p95 distance/heading limits are exceeded;
    • retain excluded-scene reports in the published quality artifact.

    The numerical distance and heading limits are derived from the corpus audit and stored in versioned configuration.

    8.4 Leakage prevention

    The implementation must make it impossible to reintroduce target drawing through a convenience path:

    • NavigationRoute has no per-sample future-waypoint field.
    • Rasterizer input is only map geometry, selected lane IDs, destination, ego pose, and geometry configuration.
    • The route corridor comes from lane centerlines, never ego future positions.
    • Lateral offsets, speed profile, acceleration, and curvature targets are not route fields.
    • Synthetic traces with different speeds and lateral offsets but the same selected lane sequence must produce the same scene-level route.
    • Perturbing a future trajectory while holding selected lane IDs fixed must not change the route raster for a fixed ego pose.
    • Artifact inspection verifies that no 64-step target coordinate array is serialized into navigation members.

    The selected route intentionally reveals navigation intent at a fork. It must not reveal the exact trajectory used as the imitation target.

    9. C++ Rasterizer

    9.1 Authority and bindings

    The C++ renderer is authoritative for both training and runtime. It exposes:

    render(
  NavigationMapView,
  NavigationRouteView,
  EgoPose,
  NavigationRasterGeometry
) -> NavigationRaster

warp(
  NavigationRaster,
  RenderPose,
  SamplePose,
  NavigationRasterGeometry
) -> NavigationRaster

    Python preprocessing calls the same library through a thin binding. The runtime can link the C++ library directly. No Matplotlib, OSMnx, network fetch, or Python plotting code is on the production path.

    A small Python reference renderer remains test-only. Golden fixtures compare Python and C++ output for:

    • ENU -> ego FLU -> pixel transforms;
    • ego anchor and crop boundaries;
    • each semantic channel;
    • direction encoding;
    • route corridor width;
    • 10 m rear clipping;
    • destination entry/exit at the crop edge;
    • adjacent-lane transition without a lateral target line;
    • level overlap;
    • invalid map and route cases;
    • 2 Hz anchor to 10 Hz sample translation/rotation;
    • newly exposed unknown pixels after a warp;
    • direction-vector rotation during a warp.

    Binary channels require exact equality. Float direction/level channels use a documented numerical tolerance.

    9.2 Determinism

    • Direct target-resolution rasterization; no 2048 pixel supersampling.
    • Stable primitive and segment ordering.
    • Fixed polygon fill and line-coverage rules.
    • No antialiasing on binary route channels.
    • No locale-dependent parsing.
    • No network or wall-clock input.
    • Same input vectors and configuration produce byte-identical artifacts.

    9.3 Runtime budget

    On the target vehicle-class reference hardware:

    • p95 C++ map+route render latency: at most 20 ms;
    • renderer resident memory increase: at most 100 MB;
    • no allocation growth over a 30 minute soak test;
    • route revision swap is atomic;
    • missed deadlines retain the previous valid raster and increment diagnostics.

    The model and vector-map cache are measured separately from the renderer budget.

    10. Flyte and Dataset Contract

    10.1 Processing location

    Scene-level route generation belongs inside Flyte data_processing, after raw scene materialization and before sample packing. It runs once per scene and is cache-keyed by:

    source revision
scene ID
map SHA-256
matcher version/config
traffic-rule config
navigation contract version
renderer version
geometry ID

    The task is fully offline and deterministic. It cannot call Overpass, Valhalla, or any external map service for KITScenes.

    KITScenes source poses are grouped onto a deterministic 500 ms anchor grid. The C++ renderer produces one map/route raster per anchor, and the production warp generates each 10 Hz sample tensor from the latest non-future anchor. Anchor timestamp, sample timestamp, and relative transform are persisted for audit.

    10.2 Shard schema v5

    KITScenes v2.2 remains immutable. This breaking contract publishes a new KITScenes v3.0 dataset after audit and full repack.

    Each scene partition contains one scene-level vector route artifact and sample members that reference its digest. Proposed members are:

    scene_navigation.json
scene_navigation_geometry.npz
navigation_quality.json

<sample_uid>.map_semantic.npz
<sample_uid>.route_mask.npz
<sample_uid>.navigation_meta.json

    The exact container may change after storage benchmarks, but these invariants do not:

    • no JPEG for semantic map or route;
    • binary channels remain lossless;
    • float direction/level channels retain exact stored float32 values;
    • route vector and provenance can regenerate every sample raster;
    • tar members and compressed containers are deterministic;
    • all content is covered by manifest hashes.

    navigation_quality.json.sample_count counts source poses used for the scene-level trace match. manifest.json.total_samples counts packed training windows after history/future eligibility filtering. These values are not expected to be equal. The packed quality audit exposes them unambiguously as trace_pose_count and packed_sample_count, and binds the scene decision to the partition through the manifest and quality-artifact hashes.

    The loader materializes:

    map_context: float32 [B, C_map, 256, 256]
route_mask: float32 [B, 2, 256, 256]
map_valid: bool [B]
route_valid: bool [B]
navigation_metadata: non-model audit data

    L2D and NVIDIA remain on their existing contracts during this milestone.

    10.3 Reasoning labels

    The initial #149 implementation does not add route information to the Reasoning teacher request or label schema. Existing 1 Hz Reasoning labels remain valid because the model's Reasoning branch receives no route input. A future Reasoning-conditioning experiment must introduce a separately versioned prompt, label artifact, and model contract.

    11. Model Integration

    11.1 Public ABI

    The forward/data API keeps the inputs separate:

    map_context
route_mask
map_valid
route_valid

    The current ambiguous map_input name is replaced as part of the breaking research-phase contract change.

    11.2 Information flow

    The initial model enforces:

    map_context -- map_valid gate --+
                                +-> channel concat
route_mask --- route_valid gate-+   -> Reactive navigation encoder
                                    -> spatial navigation features
                                    -> MapBEVFusion
                                    -> Reactive planner

visual history + ego context ------> HorizonReasoningHead
                                    -> optional ReasoningCoupling
                                    -> Reactive planner

    Map and route remain distinct inputs until validity gating. Channel concatenation provides one shared spatial encoder without conflating storage or validity semantics. Route-derived tensors must not be arguments to HorizonReasoningHead. A model unit test registers hooks and verifies this information-flow invariant.

    All encoders use semantic [0, 1] inputs without ImageNet RGB normalization. No map-specific or general encoder pretraining is added initially.

    11.3 Validity

    • map_valid=false: zero the map residual and continue camera-based planning.
    • route_valid=false: zero the route channels and use the route-less Reactive path.
    • Route-less operation must retain lane-follow behavior.
    • Validity is never inferred only from tensor contents.

    11.4 Route update behavior

    The 10 Hz Reactive call consumes the latest timestamp-aligned map and route raster. Route planning and vector resolution occur only on destination or reroute events; raster generation remains approximately 2 Hz and each model tick applies the production SE(2) warp. No route-specific neural latent cache is required for the initial Reactive-only path.

    12. Runtime Synchronization and Rendering Rate

    12.1 Clocks

    • localization input: 20 Hz;
    • authoritative C++ raster: every tenth localization update, about 2 Hz;
    • camera and Reactive planner: 10 Hz.

    This follows the useful scheduling pattern in openpilot v0.9.4, where liveLocationKalman publishes at 20 Hz for cars and the map renderer uses LLK_DECIMATION = 10. It does not copy openpilot's 2 m/px geometry.

    12.2 Timestamp alignment

    Every camera inference chooses localization and navigation state by timestamp. Route revision, camera frame, localization pose, and raster metadata are recorded in the inference result.

    A 2 Hz ego-centric raster cannot simply be held for 500 ms at 0.5 m/px. At 20 m/s that would create about 20 pixels of longitudinal error. Therefore each 10 Hz tick applies the relative localization transform:

    T_render_ego_to_camera_ego

    to warp the latest map and route raster into the camera timestamp. Binary map and route channels and categorical road level use nearest-neighbor sampling. Continuous direction channels use validity-aware interpolation and are rotated as vectors, not only spatially warped. Pixels newly exposed by the warp become unknown in the map-validity layer.

    Maximum accepted timestamp skew and raster age are versioned configuration and reported. Stale inputs are marked invalid instead of silently treated as current.

    13. Valhalla Reference Provider

    13.1 Deployment

    • Valhalla runs as a vehicle-local service.
    • Regional Valhalla tiles and OSM/lane-graph data are built before the drive.
    • Driving never fetches Overpass data.
    • Route requests occur on destination selection or rerouting, not every frame.
    • The initial request uses the auto costing model and requests route shape, maneuvers, turn-lane guidance, and a request ID.

    13.2 Provider interface

    RouteProvider.plan(
  current_pose,
  destination,
  map_version
) -> ProviderRoute

LocalLaneSequenceResolver.resolve(
  ProviderRoute,
  NavigationMap
) -> NavigationRoute

    The Valhalla adapter consumes route shape, maneuver shape indices, bearings, turn lanes, and provider attribution where available. A separate local resolver maps these to canonical directed lane segments.

    Valhalla can provide road-edge and turn-lane guidance, but not a guaranteed Lanelet2 lane ID sequence. The resolver must express uncertainty:

    • exact lane geometry available: emit selected lane IDs with high confidence;
    • only lane-count/turn-lane attribution available: emit synthesized lane segments with lower confidence;
    • no defensible lane resolution: route_valid=false for lane-level conditioning rather than inventing precision.

    13.3 Rerouting

    New routes are built under a new revision and committed atomically after validation. During computation or a transient provider failure, the previous valid route remains active. A failed replacement never partially overwrites the route currently used by the model.

    14. Evaluation

    14.1 Required training experiment

    Use the same immutable KITScenes v3.0 split, semantic map tensors, geometry, camera inputs, non-route model configuration, optimizer policy, training budget, and evaluation code for:

    1. controlled baseline with route conditioning disabled;
    2. map + Reactive-only route conditioning with production raster/warp semantics.

    Both runs use the same explicitly recorded training seed. The seed is applied to Python, NumPy, Torch, and CUDA before model construction, with a fixed cuDNN determinism policy, and is persisted in checkpoint and MLflow provenance. This controls model initialization and sample-order randomness across the two conditions without claiming cross-hardware bitwise reproducibility.

    The v3.0 split manifest inherits the exact scene, sample UID, and train/dev membership inventory from the frozen v2.2 manifest and pins that parent by SHA-256. It independently fixes the v3.0 packed-contract digest, so the comparison preserves benchmark membership without accepting legacy shards as navigation inputs.

    The legacy checkpoint remains a continuity reference, but it is not the controlled baseline because the dataset, semantic map contract, and geometry have changed. This is not a separate benchmark track. Results are added to the existing KITScenes benchmark output and MLflow run.

    Implementation completion requires a full comparable run and published analysis, even if the research hypothesis is not supported. The hypothesis is considered supported when junction/route metrics improve without an unacceptable aggregate regression.

    The frozen primary metric is wrong-branch rate on route-valid junction samples; lower is better. The route-conditioned model supports the initial hypothesis only when the paired bootstrap 95% confidence interval for conditioned - baseline is entirely below zero and neither aggregate ADE nor aggregate FDE regresses by more than 2.0% relative to the controlled baseline. At least 30 paired eligible junction samples are required. A smaller eligible count makes the result inconclusive rather than positive. These gates are fixed before the full route-conditioned result is inspected.

    14.2 Metrics

    Retain existing ADE/FDE and add:

    • ADE/FDE for junction vs non-junction;
    • ADE/FDE for route maneuver: left, right, straight;
    • wrong-branch rate at junctions;
    • predicted-path distance outside the selected route corridor;
    • selected-lane sequence compliance;
    • destination-approach error when the marker is visible;
    • valid-route coverage and invalid-route performance;
    • route-valid vs route-invalid performance delta.

    Predicted acceleration/curvature controls are integrated with the repository's vehicle dynamics before spatial route-compliance metrics are computed.

    Report bootstrap confidence intervals, corpus counts, and route-quality distribution for every slice. Do not report an improvement from a very small left/right subset without its uncertainty.

    14.3 Offline counterfactual tests

    Closed-loop simulation is out of scope, but offline counterfactuals are required:

    • hold camera/map/ego inputs fixed and swap between valid left/right/straight routes at a fork;
    • verify that the predicted controls change in the selected direction;
    • verify that blank/invalid route preserves lane-follow behavior;
    • verify that route swaps affect the planner only through the Reactive navigation encoder;
    • verify that exact future targets cannot be reconstructed from serialized route fields as described in Section 8.4.

    These focused counterfactuals do not expand the milestone into the deferred full ablation matrix.

    15. DataModelConsole

    The new KITScenes version adds:

    • route corridor overlay;
    • destination marker;
    • selected lane IDs and transition types;
    • map/route validity;
    • route confidence and quality failures;
    • map version, route ID/revision, geometry ID, and renderer version;
    • layer toggles for semantic map channels;
    • a clear distinction between ground-truth trajectory and navigation route.

    The route must never be styled as if it were the ground-truth trajectory. Desktop and mobile playback tests verify alignment, no overlap, no horizontal overflow, no browser errors, and non-empty canvas pixels.

    16. Failure Semantics

    Condition Behavior
    No destination/route route_valid=false; lane-follow model path
    KITScenes sample match failure Zero route mask, quality record, keep sample
    KITScenes scene below quality threshold Exclude from route-conditioned training, retain report
    Map missing/unknown map_valid=false; camera-only map residual
    Reroute in progress Continue previous complete route revision
    New route invalid Reject revision and retain previous route
    Raster deadline missed Reuse previous raster, warp if valid, increment diagnostic
    Raster too stale Mark map/route invalid
    Provider/map version mismatch Reject route before rasterization

    19. Acceptance Criteria

    19.1 Contract and data

    • One vector/raster ABI works with Lanelet2 and OSM adapters.
    • No serialized exact future trajectory is present in route artifacts.
    • KITScenes scene routes are deterministic and quality-audited.
    • KITScenes v2.2 is unchanged; v3.0 is a complete immutable repack.
    • Lossless artifacts regenerate byte-identical rasters.
    • Flyte and runtime use the same 2 Hz render plus 10 Hz warp path.

    19.2 Geometry and renderer

    • Map and route use the exact camera BEV XY extent and ego origin.
    • Python/C++ golden tests pass.
    • Binary route masks remain binary through storage and loading.
    • C++ p95 render is at most 20 ms and renderer memory is at most 100 MB.

    19.3 Model and runtime

    • Route information reaches the planner only through the Reactive navigation encoder.
    • Route tensors never enter HorizonReasoningHead in the initial model.
    • Map/route raster updates at about 2 Hz with timestamp warp at model ticks.
    • Route-less lane following remains functional.
    • Rerouting retains the old route until an atomic replacement is valid.
    • Local Valhalla works with prebuilt regional data and no cloud dependency.

    19.4 Research result

    • Baseline and route-conditioned models complete comparable Flyte runs.
    • Existing ADE/FDE and required route/junction slices are reported.
    • Offline route-swap counterfactuals are reported.
    • Result and uncertainty are recorded even if route conditioning does not improve the model.
    • Console displays route, destination, validity, and provenance distinctly from ground truth.

    20. Future Work

    20.1 Pretrain all encoders

    Investigate pretraining for the visual, map, route, history, and related encoders before joint AutoE2E training. This is intentionally broader than the comma.ai map-autoencoder approach and should compare frozen, partially frozen, and end-to-end fine-tuned initialization.

    20.2 Navigation robustness ablations

    Evaluate map-only, route-only, map+route, blank, shuffled, and wrong-route inputs, then add map/route dropout and localization/yaw perturbations. This follow-up owns robustness percentages and the broader ablation matrix; the initial milestone implements only the focused no-route and route-swap counterfactual checks.

    20.3 Reasoning route conditioning

    Compare the initial Reactive-only route path with Reasoning-only and combined Reactive/Reasoning conditioning. A Reasoning-conditioned variant requires a versioned route encoder, teacher context policy, and 1 Hz latent/token cache; none of those are implicit in the initial #149 implementation.
